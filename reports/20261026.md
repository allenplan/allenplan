# Week 4 Team Report
## Week 4's Goals
### Last weeks's goals
Our goals for week 4 were
- Setup CI and testing infastructure
- Create a build script which creates the extension file in one-step from the source code
- Create a clear spec for how the data is represented between our three components (UI, Scraper, Data Aggregation)

### Progress and issues
- CI and testing infrastructure were implemented primarily by James;
  see his status update for details.

- No build script is necessary to create the extension, as the standard way to load
  an in-development extension is to directly load a folder containing the extension's
  files (manifest, html, JavaScript, etc.). Since our extension contains no external
  dependencies, no build step is necessary whatsoever. There is no meaningful
  intermediate step between this and publishing an extension to each browser's
  respective extension store. Some browsers have what appear to be distributable
  extension files (e.g. Firefox has .xpi), but these files still must be signed by the
  appropriate authority. It is possible to automate the publication process, but
  it seemed premature to prioritize this over other infrastructural needs, especially
  lacking even an MVP to publish (since publication entails paying money and, with each
  new release, going through the review process).

- Finnegan, Andy, and Thomas are (to my knowledge) still exploring on what data each
  component needs and how it will use it. Demanding a spec up-front may have been
  premature, but seems more realistic now that we're gaining a better idea of
  e.g. what data is actually feasible to scrape.

I completed all of the primary goals as written and none of the stretch goals.
I performed a tiny refactor to use ES6 modules to separate browser API-dependent
code from more easily testable code, confirmed that the change didn't break
the extension, and moved the extension files into their own folder
to enable use of `node --test` for unit tests without needing to mock the browser API.
I then filled in the living document with the information required by the assignment,
including additional documentation and usage information.

Then, I coordinated with the team to ensure that team members understood and
were on board with the limitations of the suite. I offered to make modifications
if these limitations (i.e. using pure JS and not mocking the browser) would not
be adequate, but they were (initially) declined.

I encountered trouble when there was some confusion within the team regarding these
limitations (on the use of TypeScript and the testability of
code using the DOM API), but I believe we were able to arrange a short-term
mitigation (temporarily porting to pure JS and using dependency injection
and/or a pipeline architecture to minimize the amount of DOM-dependent code)
until I can potentially provide support for these features this week.

I am not currently stuck on anything; I just have other obligations I need to
attend to before resuming work here.
