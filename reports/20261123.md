### James Martin
#### Last week's goals
None declared.

#### Progress and issues
I worked with Finn to implement a UI overhaul. It replaces the old tab-based UI
with a new contextual UI that offers options based on the current state of the
program (e.g. whether or not an input has occurred yet) and what page the user
is on (e.g. don't offer "Open DARS" if you're already on DARS). It automatically
opens relevant pages to reduce total button clicks (e.g. automatically opening
the planner after importing a schedule). Finally, it ensures that you can only
import Allen school majors, as only those are supported. Overall, I believe this makes the user
interface much more user friendly. I'd been advocating for this change for several
weeks, so it's a relief to see it implemented (by me, no less!).

Although the implementation was done with Codex, this change required substantial (a couple hours)
up-front planning, including two rounds of feedback with Codex before even touching
implementation. Additionally, Codex made dubious design decisions and several
mistakes, so the redesign required substantial iteration over several hours.
Finn was curious at several stages what would happen if we just prompted Codex to
do whatever was left on its own, including providing the design document we created,
and it generally did a poor job, so I'm satisfied with my ownership of this change
and that Codex (Astra High) can't replace me yet.

Additional features include reusing the planner instead of opening new ones each
time, storing the date and time and major imported, and saving schedule
preferences. These were innovations by Codex, and I like all of them.
My one criticism is that reusing the planner makes it impossible to
compare generated schedules side-by-side (with e.g. different preferences,
majors, or DARS imports (since DARS import is affected by MyPlan, I think)).
When I brought this up, Codex recommended giving the option to copy the
planner so that reusing the primary/working planner doesn't lose data. I think
this is a reasonable design, if perhaps unnecessarily complicated compared
to just generating new planners that each own a copy of the import data and
preferences they were created with. I'm not sure which is preferable (it probably
depends on how common we expect the side-by-side comparison use case to be--
realistically probably not very, based on current limitations), but one of
them ought to be implemented by Finn or me. I didn't do it at the time
because I didn't want feature creep in the change I was asking Finn to review.

#### Plans and goals for the next week
We'll see based on how this meeting goes. TypeScript, CI, and tooling becomes decreasingly
relevant as we approach the end of the project, so it may be more worthwhile
to have me work on features again.
