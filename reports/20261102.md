  * Survey team members/existing code for how valuable this kind of testing is would be (2 units)
  * Implement automated (possibly cross-browser) testing (or not) (between 0 and 4 units, depending on previous steps)

#### Progress and issues
I've figured out how to use `npm` to:

* run the TypeScript compiler including types for the DOM API and WebExtensions API,
* run a TypeScript linter and formatter, and
* include JavaScript/TypeScript dependencies from npm in an extension-compatible way.

Since TypeScript supports incremental compilation, enabling TypeScript seems like a no-brainer.

The main problem is that we're on the cusp of our demo release, but these changes require 
changing all of the files all at once (e.g. moving folders, changing file extensions,
style fixes for tons of files), and I don't want to block progress with nightmare
merge conflicts, so I'm blocked until the demo is ready and things have settled down.

The key ideas of the deferred implementation plan are:

* use TypeScript 6.X (7.0 lacks linter/formatter support),
* to add ["es2017", "dom"] to the TS compiler libs for DOM API support,
* to add "firefox-webext-browser" to the TS compiler types for WebExtensions support (cross-browser despite the "firefox" in the name),
* migrate from the chrome namespace to the browser namespace (miniscule change),
* use `gts` for the linter/prettifier/fixer (comes pre-bundled with Google style settings),
* use `esbuild` to bundle dependencies (chunked) and copy non-JS/TS files,
* figure out how to port the test suite (I'll figure it out when I get there--maybe I can still get away with using Node's framework),
* apply automatic fixes/formatting and manually apply remainder (plus any type annotations I can infer),
* add the new linter checks to GitHub actions,
* add files like .editorconfig to ensure recommendations are applied automatically when possible,
* write documentation for how to use all this stuff,
* ensure team members are on board with enforcing style and type annotations more strictly going forward.
* If I wanted to be more totalitarian, I could also enforce that the CI passes to merge into main
  or set up other kinds of stuff like pre-commit hooks.

I also provided some testing data for Andy, created a new status report template,
and generally contributed to discussions at team meetings.

Finally, I ported the extension to Firefox. That was a no-op.
It again turns out that the WebExtension API / Manifest V3 makes it difficult
*not* to write a portable extension.

#### Plans and goals for the next week

I don't think precise time estimates really matter because the whole thing needs to be done
